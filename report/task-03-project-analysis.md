# Задание 3. Исследование структуры кросс-платформенного проекта

## Исследуемый проект

Для анализа выбран официальный пример Tauri API из репозитория
tauri-apps/tauri, расположенный в каталоге examples/api.

Адрес репозитория: https://github.com/tauri-apps/tauri
Каталог примера: examples/api
Дата обращения: 15.10.2026
Коммит: 152d293ddf5680b968dc4853e52d87c12a2deaeb

Пример демонстрирует возможности API Tauri. Веб-интерфейс
реализован с использованием Svelte и TypeScript, а нативная
часть — на Rust. Для веб-сборки используется Vite.

Проект исследуется без запуска и сборки.

Пример входит в монорепозиторий Tauri и использует его общие
компоненты: локальные зависимости JavaScript и зависимости Rust,
наследуемые из Cargo workspace.

## Особенности конфигурации

1. Веб-часть использует Svelte и TypeScript. Команды dev и build
   запускают Vite.

2. JavaScript API Tauri подключается по относительному пути
   ../../packages/api/dist, а команда Tauri CLI использует файл
   ../../packages/cli/tauri.js. Это указывает на связь примера
   с остальной частью монорепозитория.

3. Rust-зависимости tauri и tauri-build наследуются из Cargo workspace.
   Поэтому их конкретные версии нельзя определить только
   по Cargo.toml исследуемого примера.

4. Каталог ../dist указан как источник собранного веб-интерфейса.
   Перед запуском и сборкой конфигурация предусматривает команды
   pnpm dev и pnpm build. Наличие npm на компьютере не означает,
   что все зависимости этого примера уже подготовлены к сборке.

5. Для Windows в tauri.conf.json заданы параметры установщиков
   WiX и NSIS. Для WiX подключена локализация pt-BR.

6. Зависимость tauri-plugin-automation объявлена только для целей,
   отличных от Android и iOS. Дополнительно она является
   необязательной и включается возможностью automation.

7. Мобильные каталоги android/ и ios/ в исследуемом дереве
   относятся к вложенному примеру плагина, а не к отдельным
   корневым проектам приложения.

8. Значения version в package.json, Cargo.toml и tauri.conf.json
   описывают версии соответствующих компонентов примера.
   Их нельзя использовать как актуальную версию фреймворка Tauri.

## Обращения к платформенным возможностям

### 1. Управление нативным окном через общий API

Файл: src/views/Window.svelte.

```typescript
function setTitle() {
  selectedWebview.setTitle(windowTitle)
}
```

```typescript
function minimize() {
  selectedWebview.minimize()
  setTimeout(selectedWebview.unminimize, 2000)
}
```

Веб-интерфейс обращается к возможностям нативного окна через API Tauri:
изменяет заголовок, сворачивает и восстанавливает окно. Общий код
вызывает единые методы, а взаимодействие с конкретной ОС обеспечивает
Tauri. Таким образом, обращение к платформенным возможностям не всегда
требует отдельной реализации интерфейса для каждой ОС.

### 2. Условная логика интерфейса в зависимости от ОС

Файл: src/views/Window.svelte.

```typescript
const isWindows = navigator.appVersion.includes('Windows')
const isMacOS = navigator.appVersion.includes('Macintosh')
```

```typescript
const effectOptions: Effect[] = isWindows
  ? windowsEffects
  : (Object.values(Effect) as Effect[]).filter(
      (e) => !windowsEffects.includes(e)
    )
```

В разметке блок настройки эффектов отображается условно:

```svelte
{#if isWindows || isMacOS}
```

Пример проверяет строку navigator.appVersion и в зависимости от
результата выбирает набор эффектов. Панель эффектов отображается только
при распознавании Windows или macOS.

Это платформенное ветвление внутри общей веб-кодовой базы. Наличие
общего файла не означает, что все его возможности одинаково доступны
на каждой платформе. При анализе важно также учитывать, что проверка
строки браузерного окружения не равнозначна проверке поддержки
конкретного эффекта.

### 3. Выбор реализации плагина при компиляции

Файл: src-tauri/tauri-plugin-sample/src/lib.rs.

```rust
#[cfg(desktop)]
mod desktop;
#[cfg(mobile)]
mod mobile;
```

```rust
#[cfg(desktop)]
use desktop::Sample;
#[cfg(mobile)]
use mobile::Sample;
```

В зависимости от целевой категории платформы подключается модуль
desktop или mobile. Условие обрабатывается при компиляции,
а не во время выполнения приложения.

Общая часть плагина использует тип Sample, но его реализация выбирается
для соответствующей категории платформ. Аналогичное разделение
применяется при инициализации плагина.

### 4. Возможность, реализованная только на мобильных платформах

Файл: src-tauri/tauri-plugin-sample/src/lib.rs.

```rust
#[cfg(mobile)]
return app.sample().js_values().map_err(|e| e.to_string());

#[cfg(desktop)]
{
  let _ = app;
  Err("js_values is only implemented on mobile".into())
}
```

Команда js_values имеет различное поведение в зависимости от целевой
платформы. На мобильной платформе вызывается реализация метода,
а на настольной возвращается ошибка об отсутствии реализации.

Этот фрагмент показывает ограничение переносимости: команда
зарегистрирована в общем интерфейсе плагина, но соответствующая
функциональность доступна не на всех платформах.

## Вывод

Системные требования Tauri:
https://v2.tauri.app/start/prerequisites/
Дата обращения: 15.10.2026.

Исследованный пример Tauri API использует веб-технологии для интерфейса
и Rust для нативной части приложения.
По классификации инструментов он относится к категории веб-технологий
и WebView-обёрток.
Переносимость обеспечивается общим веб-интерфейсом, API Tauri
и сборкой нативной части под целевую платформу.
Общая веб-кодовая база размещена преимущественно в каталоге src.
Каталог src-tauri содержит нативный код, настройки и компоненты,
среди которых необходимо различать общие и платформозависимые части.
Поэтому считать весь Rust-код платформозависимым некорректно.
В компоненте Window.svelte обнаружены обращения к нативным окнам
через единый API, а также условный выбор возможностей в зависимости
от распознанной ОС.
В примере плагина разделение настольной и мобильной реализаций
осуществляется при компиляции через атрибуты cfg.
Команда js_values демонстрирует функциональное ограничение:
на настольных платформах она возвращает сообщение об отсутствии реализации.
Количественная доля общего кода не измерялась, однако структура показывает
повторное использование веб-компонентов и общей оболочки плагина
при наличии выделенных платформенных реализаций.
При переносе на дополнительную платформу требуется проверить поддержку
Tauri, системные зависимости, работу оконных функций и реализаций плагинов.
Для Astra Linux необходимо отдельно проверить совместимость конкретной
версии дистрибутива с зависимостями Tauri, включая WebKitGTK,
и выполнить тестирование приложения в целевой среде.
Перенос на ОС «Аврора» нельзя считать автоматически обеспеченным
наличием мобильной реализации плагина: для него необходим отдельный
анализ инструментальной поддержки и платформенных интеграций.
